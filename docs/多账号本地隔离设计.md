## 1. 问题诊断

### 1.1 现象（用户真机反馈）

- 已删除的书籍在本地仍保留阅读页面记录（进度未清）。
- 同设备切换账号后，重新添加一本以前加过的书，**打开报错**。
- 系统尝试从云端下载该书，但因为此前在该账号删除过，**书籍不再上传到云端** → 下载 404 → 报错。

### 1.2 根因：账号专属的同步账本被塞进了设备共享的本地库

| 东西 | 现状 | 证据 |
|---|---|---|
| 本地库 | 单个 `library.db`，books 表**无 user_id** | `lib.rs` `init_db` / setup |
| 文件本体 | 内容寻址 `books/<hash>.pdf`，全设备共享 | `lib.rs` `add_one_book` |
| 拉取游标 | `sync_meta.pull_cursor` 设备级**单值** | `sync_engine.rs` `get_cursor/set_cursor` |
| synced_at / cloud_state | 存每行上，语义却是「相对某账号」 | books 行内列 |
| **账号切换** | SignIn/Out **只清 token + 状态**，不碰 books / synced_at / cloud_state / cursor | `sync_runtime.rs` 命令分支 |

一句话：本地库、文件、拉取游标、每行的 `synced_at`/`cloud_state` **全是「每设备一份、不分账号」**，而 `synced_at`/`cloud_state`/`cursor` 的语义本应「相对当前登录账号」。账号切换不重置其中任何一项 → 上一个账号的同步账本污染下一个账号。

### 1.3 故障链复现

1. **账号 A** 加书 X → 上传 → `cloud_state` 变 `synced`/`remote`、`synced_at` 设值、cursor 前进。
2. **A 删 X** → 墓碑推云端（云端 A 行 `deleted=true`）、删本地文件；**但 R2 对象未删**。
3. **切到账号 B**（只清了 token）→ 本地 X 行仍在：`deleted=1`、`cloud_state=synced/remote`、`synced_at=A 的值`、`cursor=A 的值`。
4. **B 重新加 X**（同文件）→ 命中 `deleted=1` → `revive` 复活：`deleted=0`、复制文件回 `books/X.pdf`、`updated_at=now`；**但 `cloud_state` 未重置**。
   - `collect_uploadable` 只挑 `cloud_state='local'` 的 → **X 永不上传到 B 的云/R2**。
   - 但 `collect_dirty` 会把**元数据**推给 B 云端 → B 云端有 X 元数据行，**R2 里却没有文件**。
   - `cloud_state='remote'` 时前端 `tryOpenBook` 判为云端书 → 去下载而非打开本地已存在的文件 → GET `{B}/books/X.pdf` → **404 → 报错**。
5. 附带：B 用了 A 的 cursor → B 的增量拉取从 A 的高水位开始，B 在此之前的云端行**永远拉不回**（静默丢数据）。

## 2. 决策

### 2.1 方案选型

核心矛盾：**D1 要「本地优先、账号可选」，但当前把账号专属的同步账本混进了设备共享的本地库。** 要么隔离本地库，要么隔离账本。

| 方案 | 做法 | 结论 |
|---|---|---|
| **A（采纳）** | 本地库**按账号隔离** + 匿名库；切号热切换连接 | 干净、天生对齐云账本、无跨账号污染；改动较大 |
| B | 单库，切号时重置账本（清 cursor / synced_at 归零 / cloud_state 复位） | 半修：本地书目仍全账号可见、删改互相串。否 |
| C | 登出即清空已同步数据（云优先） | 违反 D1（离线书消失）。否 |

**用户 2026-07-24 拍板：方案 A。**

### 2.2 关键决策点（已确认）

- **(a) 文件按账号隔离**：文件也放进 `accounts/<key>/books/`，**不做共享 + 引用计数**。彻底隔离、无 refcount 复杂度；代价是同一本书两账号各存一份（个人规模磁盘可忽略）。日后可优化成 hash 共享 + refcount（见 §8）。
- **(b) R2 孤儿文件清理**：删书只删元数据不删 R2 对象 —— **留作后续独立任务**（隔离后多账号症状已消，此属存储卫生），不塞进本次以免膨胀。见 §8 / MA-8。
- **(c) 分两阶段提交**：先骨架（目录/迁移/启动选账号），再切换协调 + 前端 + revive 修复；每阶段各自 CI 绿。

### 2.3 与既有决策的关系

- **D1（本地优先、账号可选）**：匿名库 = 未登录时的完整本地书房，强化而非违反 D1。
- **D3（书籍 ID = SHA-256）**：不变。隔离在「库/目录」层，hash 仍是书籍身份。
- **D10（本地 DB 存相对路径 `books/<hash>.pdf`）**：不变。相对路径现在相对「账号目录」，迁移只是移动 base，路径无需改写。

## 3. 目标架构

### 3.1 目录布局

```
<base>/
  accounts/
    <user_id>/            # 登录账号；user_id 是 UUID，文件系统安全
      library.db
      books/<hash>.pdf
      covers/<hash>.jpg
    anonymous/            # 未登录：完整本地书房（符合 D1）
      library.db  books/  covers/
```

`account_key` = 登录时的 `session.user_id`（UUID），未登录时固定字面量 `"anonymous"`（真实 key 为 UUID，无冲突）。

### 3.2 数据结构（`lib.rs`）

把 `db / base_dir / books_dir / covers_dir` 收进一个可整体替换的 `Active` 束：

```rust
struct Active {
    db: Connection,
    base_dir: PathBuf,     // = <base>/accounts/<key>
    books_dir: PathBuf,
    covers_dir: PathBuf,
    account_key: String,
}

struct AppState {
    active: Mutex<Active>,
    dict: Mutex<Option<Connection>>,   // dict 不随账号变，维持原样
    root: PathBuf,                      // = <base>，用于推导账号目录
}
```

新增辅助：`fn open_account(root: &Path, key: &str) -> Result<Active>`（建 `accounts/<key>/{books,covers}` 目录 → `init_db` → 返回 `Active`）。

18 处 `state.db` / `state.base_dir` / `state.books_dir` / `state.covers_dir`（约 10 个命令）改为先 `let a = state.active.lock().unwrap();` 再取字段（机械改动）。

### 3.3 账号切换协调（核心难点：两条连接同时切）

`sign-in` / `sign-up` / `sign-out` 命令变成**编排者**，一步做完：

```
前端 AccountPanel → sync_sign_in(email,pwd)
  1. 经 sync 引擎完成认证（引擎线程 backend.sign_in）
     —— SignIn/SignUp 的 reply 改为返回 user_id（现在只回 ()）
  2. 成功后本地切换：
     - AppState.active ← open_account(root, user_id)
     - asset_protocol_scope.allow_directory(新 books_dir / covers_dir)
  3. 给引擎发新命令 SwitchAccount{ db_path } → engine_loop 重开自己的 db 连接 + base_dir
  4. app.emit("library-changed")
前端 Library 监听 library-changed → reload()
```

登出对称：切回 `accounts/anonymous/`。

> **为何两条连接**：UI 连接（`AppState.active.db`）与同步引擎连接（`engine_loop` 自持，WAL 多连接）指向同一 `library.db`。切号必须**两条一起**指向新账号的库，否则一方写旧库一方写新库。

### 3.4 启动选账号（`setup` + `engine_loop`）

- `setup` 里先 `token_store::load_session()` 读 `user_id`（**不 refresh**）：有则开 `accounts/<uid>/`，无则 `anonymous/`；用同一 `db_path` spawn 引擎。
- 引擎照旧 refresh 校验；若失效则清 session、`signed_in=false`，**AppState 仍停在该账号目录**（书在、暂不同步，重新登录即续）。此行为写入代码注释。

### 3.5 迁移（一次性，仿现有 `migrate_old_base`）

- **判据**：`<base>/library.db` 存在 **且** `<base>/accounts/` 不存在。
- **目标账号**：迁移时若钥匙串有 session → 移进 `accounts/<该 user_id>/`（保住登录用户连续性）；否则 `anonymous/`。
- **动作**：建目标目录，把 `library.db` + `books/` + `covers/` 整体 `rename` 进去（D10 相对路径不受影响）。
- **异常**：任一步失败回退（不删源、不半迁），下次启动重试。

## 4. 技术细节

### 4.1 `lib.rs`

- `open_account(root, key)`：`create_dir_all(accounts/key/{books,covers})` → `init_db(accounts/key)` → 组 `Active`。
- `resolve_account_key_at_startup(app) -> String`：读 keyring session 的 user_id，无则 `"anonymous"`。
- `migrate_to_account_layout(root, key)`：判据 + 整体 rename + 异常回退；纯函数便于单测（仿 `migrate_old_base`）。
- `AppState` 重构 + 18 处字段访问改走 `active.lock()`。
- `revive_deleted_book_record` 增加重置（见 4.4）。
- setup：`key = resolve_account_key_at_startup`；`migrate_to_account_layout`；`active = open_account(root, key)`；`spawn(app, root/accounts/key/library.db)`。
- sign-in/up/out 编排命令：注入 `State<AppState>` + `AppHandle` + `State<SyncHandle>`，完成 §3.3 步骤 2–4。

### 4.2 `sync_runtime.rs`

- 新增 `SyncCommand::SwitchAccount { db_path: PathBuf, reply }`。
- `engine_loop`：把 `db` / `base_dir` 由 `let` 改为可变，`SwitchAccount` 分支里 `Connection::open(new_path)` 重赋值 + 重设 `busy_timeout` + 重算 base_dir；切换后重置本轮 pending / failures。
- `SignIn` / `SignUp` 分支：reply 类型由 `Result<(), String>` 改为 `Result<String, String>`（返回 `session.user_id`）。`SyncHandle::request` 相应泛化或加一个返回值的变体。

### 4.3 前端（`api.ts` / `AccountPanel.tsx` / `Library.tsx`）

- `api.ts`：`syncSignIn/Up` 返回类型若带 user_id 则透传（供前端可选使用；主要切换在 Rust 侧完成）。
- `Library.tsx`：`useEffect` 里 `listen("library-changed", () => reload())`，卸载时取消。
- `AccountPanel.tsx`：登录/登出成功后无需自己刷新书库（靠 `library-changed` 事件），仅更新账号面板状态。

### 4.4 revive / tombstone 修复（独立正确性，随本次并入）

- `revive_deleted_book_record` 复活时额外置：`cloud_state='local'`、`synced_at=0`、`current_page=1`。
  - **理由**：即便单账号，删（墓碑推云端 `deleted=true`）后重加，复活行有真实本地文件，应被当「全新本地书」重新上传（`cloud_state='local'` 才进 `collect_uploadable`），且不应让旧阅读进度诡异复活。

## 7. 风险与守护

| 风险 | 守护 |
|---|---|
| 连接热切换时引擎正跑 cycle（锁竞争/半写） | 切换命令走引擎命令通道串行处理；切换前置 pending/failures 复位；UI 侧 `active` 换连接持锁完成 |
| asset scope 未授权新账号目录 → 封面 403 | 切换时 `allow_directory` 新 books/covers（镜像 setup 逻辑，§4.2 坑对照） |
| 迁移中途失败 | 纯函数 + 全异常回退（不删源、不半迁），仿 `migrate_old_base` |
| 启动 session 失效仍停在账号目录 | 明确记录为预期行为（书在、暂不同步、重登即续）；不静默切 anonymous 以免误藏书 |
| WKWebView / iOS 容器路径变化 | 相对路径 D10 已覆盖；账号目录同样在 app 数据容器内 |

## 8. 后续项详述

- **MA-8 R2 孤儿**：当前 `remove_book` 仅删元数据 + 本地文件，云端 R2 `{user}/books/<hash>.pdf` 遗留，长期占配额。方案：墓碑 push 时对已上传（`cloud_state` 曾为 synced）的书发 sign-url DELETE 清 R2；失败退避重试。与本次隔离改动正交。
- **MA-9 共享文件 + refcount**：隔离后同书跨账号各存一份。若需省盘，改回 `<base>/books/<hash>.pdf` 全设备共享 + 设备级引用计数表（哪些账号引用此 hash），删末个引用才删物理文件。复杂度高，仅在磁盘成为问题时做。
